# 36 — 보고서 RAG 처리·활용 검토

작성 2026-10-19 · 상태: **검토만(구현 전)** · 사용자 요청: "이제 Rag를 어떻게 처리하고 활용 가능할지 검토해줘."
실데이터·실색인은 열지 않고 22 코드(`report_index/`, `routers/reports.py` 의 `/answer`)만 읽고 판단했다.

## 1. 지금(22)
| 단계 | 현재 | 판단 |
|---|---|---|
| 추출 | PDF·DOCX·XLSX·PPTX + OCR, 쪽·시트 위치 보존 | 충분 |
| 조각 | 쪽 단위, 1,800자(`extractors.py`) | 조각에 보고서 제목·호선 같은 맥락이 없다 |
| 검색 | FTS5 trigram + bge-m3 벡터 | 순위는 보고서 단위 |
| 답변 | 검색 상위 보고서 20 → 보고서마다 낱말 맞는 조각 앞에서부터 → 16발췌·1만 자 → qwen2.5:7b | 질문에 가까운 조각을 고르지 않는다 |
| 검증 | 답의 [S#] 가 준 발췌인지만 | 숫자·재질 기호는 대조하지 않는다 |

## 2. 약한 곳
1. 질문 문장 전체를 낱말 OR 로 찾는다 — '결과'·'만족' 같은 흔한 낱말이 거의 모든 보고서에 걸린다.
2. 조각 단위 순위가 없다(보고서를 먼저 고르고 그 안에서 낱말 맞는 조각 순서).
3. LogBook 의 구조 정보(호선·구역·해석 종류·문서 분류)를 질문 해석에 쓰지 않는다 — 가장 큰 개선 여지.
4. 7B 모델은 숫자를 틀리기 쉽다 — 해석 보고서의 핵심이 숫자다.
5. Ollama 를 WorkBench AI 와 나눠 쓴다(요약 동시 사용자 1 · 전체 2) — 대량 처리는 야간.

## 3. 처리 제안
- **A 조각 맥락**: 임베딩 전에 "보고서 제목 | 호선 | 해석 종류 | 쪽" 을 붙인다. 전 조각 재임베딩(야간 1회).
- **B 질문 해석**: 호선 번호·구역·해석 종류를 규칙으로 뽑아 먼저 거르고, 나머지 문장으로 검색.
- **C 조각 단위 혼합 순위**: FTS 순위와 벡터 순위를 RRF 로 합쳐 상위 10~16 조각을 근거로.
- **D 숫자 대조**: 답의 숫자·재질 기호(AH36 등)가 인용 발췌에 실제로 있는지 검사, 없으면 표시.
- **E 사실·개념 추출(야간 배치)**: 보고서마다 재질·판두께·허용응력·안전율·하중 조건·만족 여부·개념 언급을 근거 위치와 함께 표로(34 의 재료).
- B·C·D 는 LLM 호출을 늘리지 않는다. E 만 무겁다 — 145 에서 보고서 20건으로 처리 속도를 먼저 잰다(지금은 추정 근거 없음).
- 재순위 모델(reranker)은 Ollama 만으로는 어렵고 새 패키지가 필요 — 평가 결과를 보고 정한다.

## 4. 활용(효과 순)
1. 근거 질의응답(A~D) — 보고서·쪽 인용.
2. 사실 비교표(E) — 호선별 판두께·재질·안전율·만족 여부, 칸마다 근거 쪽으로.
3. 등록 시 정보 제안 — Inbox 보고서의 해석 종류·호선·구역·문서 분류 미리 채움.
4. 판 차이 요약 — 32 `page_changes` 의 바뀐 쪽만 LLM 요약.
5. 비슷한 과거 사례 — 32 평균 벡터 재사용.
6. 34 옵시디언식 지도·백링크 — E 결과.
2·3·6 은 같은 사실·개념 표를 쓴다.

## 5. 평가 먼저
실제 질문 30~50개 + 정답 보고서·쪽(사용자가 질문을 준다). 지표 = 정답 쪽이 상위 10 안에 드는 비율, 바꾸기 전·후로 잰다.

## 6. 위험
OCR 숫자 오류(원문 확인), 권한은 사실 표도 요청마다 MySQL 로 다시 확인, 모델은 사내 Ollama 만(외부 API 금지),
'발췌 근거 답변 — 전체를 읽은 것이 아님' 안내 유지. 지금 Vault 보고서는 10건 안팎(32 문서) — 효과는 쌓인 뒤.
