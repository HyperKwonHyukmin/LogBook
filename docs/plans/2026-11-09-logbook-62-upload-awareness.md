# 62 — 올리기 · 정리 · 확정 과정의 인지 틈 메우기

2026-11-09 사용자 요청: "올리면 정리 대기에서 업로드가 진행되고, 분류를 정하고 확정을 누르는 전 과정을 사용자가 알 수 있어야 한다.
업로드 중인 줄 모르고 두 번 올리거나, 진행 중인데 안 된다고 생각하는 틈이 없는지 검토."

## 검토 결과 (코드 기준)

이미 잘 보이는 것 — 브라우저 전송(가운데 카드 % · 취소 · 이어 올리기 · 단추 잠금 · 두 번째 놓기 안내 · 창 닫기 경고 · 화면 이동 뒤에도 카드),
서버 정리(staged 진행 패널 · 단계 · 남은 시간 · 워커 꺼짐), 동일 BDF(확정 · 초안 모두와 비교, 17).

남은 틈과 처리:

| # | 틈 | 처리 |
|---|---|---|
| ① | [확정]이 단추만 잠기고, 성공하면 카드가 말없이 사라짐 | 단추가 「확정하는 중…」(스피너), 끝나면 토스트 「확정했습니다: E… ‘제목’」 + [자료 보기] (`DraftCard` `onConfirmed` → `InboxPage`). 다른 자료에 추가(merge)면 「… 에 파일을 추가했습니다」 |
| ② | 다른 화면에서는 확정 안 한 초안이 남았는지 모름(검색에 '미분류'로 보여 올라간 줄 앎) | 사이드 메뉴 '정리 대기'에 내 초안 수 배지(주황), 올리는 중·정리 중이면 작은 스피너. 마우스를 올리면 「처리 중 N묶음 · 확정할 초안 N건」 |
| ③ | 보고서 등 BDF 가 아닌 파일은 확정 자료(vault)하고만 비교 — 확정 전에 같은 폴더를 두 번 올리면 경고 없이 초안 둘 | `ingest/process.py` 가 다른 묶음의 **정리 대기 초안 파일**(staging · draft)과도 sha256 비교(확정 자료를 먼저 가리킨다). 화면은 기존 「E… 에 이미 있음」 칩, 확인할 것 문구는 「이미 올라온 파일 N개: 같은 파일이 다른 자료·초안에 있습니다」 |
| ④ | 폴더 창에서 같은 폴더를 또 올리는 줄 모름 | 폴더 이름이 내 진행 중 묶음(올리는 중 · 정리 중 · 확정 전 초안 있음)과 같으면 폴더 창에 경고 한 줄(막지 않음) |
| ⑤ | 브라우저가 보내는 중(uploading)인 묶음은 그 창에서만 보임 — 다른 탭 · PC · 새로 고침 뒤에는 흔적 없음 | 정리 대기 화면에 「다른 창(또는 다른 PC)에서 올리는 중인 묶음이 N개 있습니다 …」 한 줄(서버 uploading 수 − 이 창의 올리는 중 · 멈춘 올리기 수). 24시간 지난 것은 세지 않는다(`cleanup_stale`) |

새 API — `GET /api/batches/summary`(로그인 누구나, 내 것만):
`{ drafts, staged, uploading, names: [{name, state, received_at}] }`. 셸의 `InboxSummaryProvider`(`components/shell/InboxSummary.jsx`)가
30초마다(탭이 보일 때) · 화면 이동 · 이 창의 올리기 시작/끝(`GlobalDrop`) · 정리 대기 목록을 다시 부를 때 읽는다.

새 패널은 늘리지 않았다 — 기존 단추 · 메뉴 · 토스트 · 폴더 창에 상태만 실었다.

## 2부 — 확정 자료에 [파일 추가] (같은 날 추가 검토)

| # | 틈 | 처리 |
|---|---|---|
| A | 올리는 도중 패널을 닫거나 화면을 떠나면 결과를 따라가지 않아 목록이 새로 고쳐지지 않음 | 이 자료로 올리는 중(셸 저장소 `entry:E…`)이거나 서버가 붙이는 중이면 패널을 닫지 않고 단추가 「파일 추가 중…」. 자료 응답에 `pending_additions`(내가 이 자료로 붙이는 중인 묶음)를 실어, 돌아오면 패널을 열고 이어 따라간다. 끝나면 토스트 |
| B | 「붙이는 중…」 한 줄뿐, 5분 뒤 확인을 멈춤 | 정리 대기와 같은 말(`stagedStatus` — 앞 배치 N개 · 워커가 하던 작업 · 파일 확인 n/N). 2분 뒤부터 10초마다 계속, 30분 넘으면 [다시 확인] |
| C | 무엇이 붙었는지 안 보임 | 묶음 응답 `added`(실제로 붙은 파일) → 「파일 N개를 이 자료에 추가했습니다」 + 목록에 「새 파일」 표시(이 화면에 있는 동안) |
| D | 같은 이름이면 말없이 `이름 (2)` | 합칠 때 배치 `excluded` 에 `{reason: 'renamed', name, to}` 를 남기고 결과에 「같은 이름이 있어 새 이름으로 저장: a → a (2)」. 올리기 전에도 패널 문구와 폴더 창(파일 추가 모드)에 「이 자료에 같은 이름의 파일이 N개」 |
| E | 이 자료에 이미 있는 똑같은 파일(BDF 아닌 것)이 `(2)` 로 한 벌 더 | `entries.service.confirm` 의 합치기 경로가 대상 자료의 vault 파일과 sha256 이 같은 파일은 붙이지 않고 `95_Trash/draft_<초안>_same_<시각>/` 로 옮긴다(`{reason: 'duplicate_in_entry', name, of}`). 모두 같으면 아무것도 붙이지 않고(version · 감사 기록 없음) 초안만 정리 |

덮어쓰기(교체)는 넣지 않았다 — 옛 파일이 사라지면 판(R0 → R1) 흐름과 감사 기록이 끊긴다. 새 이름으로 남기고 분명히 알린다.
E 는 정리 대기에서 [이 자료에 추가]로 확정하는 초안에도 같이 적용된다(같은 합치기 경로).

## 남은 것 · 한계

- 화면을 눈으로 보지 않음 — 개발 DB 에 초안이 없고, 개발 PC 저장소가 운영 공유 폴더라 시험 자료를 올리지 않았다. 145 에서 확인.
- ③ 은 새로 올리는 묶음부터 적용(이미 있는 초안의 표시는 바뀌지 않는다). 탐색기로 `00_Inbox` 에 넣은 묶음(주인 없음)은 배지 · 이름 경고에 세지 않는다.
- 여러 탭에서 같은 계정으로 올리면 ⑤ 의 '이 창' 수 계산은 탭마다 따로라, 각 탭이 서로를 '다른 창'으로 센다(의도한 동작).
