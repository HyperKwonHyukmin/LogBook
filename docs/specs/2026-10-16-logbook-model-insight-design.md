작성 2026-10-16. 관계 지도(25) 다음 단계로 검토한 세 기능의 구현 설계다.

> **번호 정정(같은 날 구현).** 비슷한 선례를 `model_features` 표 없이 이미 있는 `model_summaries` 만으로 만들 수 있어 먼저 구현했다.
> 그래서 **26 빈칸 지도 · 27 비슷한 선례 · 28 모델 특징 + 모델 점검** 순서다. 아래 본문의 '27 모델 점검'은 28, '28 비슷한 선례'는 27 로 읽는다.
> 구현 계획서: `docs/plans/2026-10-16-logbook-26-coverage.md`, `…-27-similar.md`.

| 제안 번호 | 기능 | 한 줄 | 새 데이터 |
|---|---|---|---|
| **26** | 빈칸 지도 | 무엇이 **없는지** 보인다 | 없음 — 이미 있는 값만 센다 |
| **27** | 모델 특징 + 모델 점검 | 확정 전에 **수상한 모델**을 알린다 | `model_features` 표 1개(변환 때 계산) |
| **28** | 비슷한 선례 찾기 | **BDF가 곧 검색어**가 된다 | 27의 특징을 그대로 쓴다 |

관계 지도와 같은 원칙을 따른다.
- 사람에게 새로 입력받지 않는다. 변환·서명·분류처럼 이미 쌓이는 값으로 계산한다.
- 이유를 문장으로 보여 준다. 관계 지도에서 선에 올리면 "왜 이어졌나"가 나오듯, 점검 경고와 비슷한 선례에도 "왜"가 붙는다.
- 권한 거르개(`access.visible_entries_filter`)를 모든 집계에 건다. 보이지 않는 자료는 개수에도 섞이지 않는다.
- 막지 않고 알린다. 점검 결과로 확정을 막지 않는다(17번 '똑같은 BDF 차단'만 예외로 남는다).

진행 순서는 **26 → 27 → 28**을 권한다. 26은 바로 만들 수 있고, 28은 27의 특징 표 위에 선다.

## 26. 빈칸 지도 (`/coverage`)

### 무엇을 보여 주나
관계 지도가 "무엇이 이어져 있나"라면, 빈칸 지도는 "무엇이 비어 있나"를 보여 준다.

**① 격자** — 행은 호선(또는 프로젝트·공용), 열은 구역(분류 목록의 대표 값)이다. 칸 하나 = 그 호선 × 구역의 확정 자료.
위쪽 거르개로 해석 종류를 고르면 그 종류만으로 칸을 다시 칠한다.

| 칸 상태 | 뜻 | 표시 |
|---|---|---|
| 갖춤 | 모델 + 문서가 있고 해석 검증 통과(또는 미실행) | 남색 칸 + 자료 수 |
| 문서 없음 | 모델만 있다 | 옅은 남색 + `문서 없음` |
| 모델 없음 | 문서만 있다 | 테두리 칸 + `모델 없음` |
| 검증 실패만 | 모델이 전부 해석 검증 fail/error | 주황 점 + `검증 실패` |
| 비어 있음 | 자료 없음 | 빈 칸(점선) |

색만으로 구분하지 않는다(PRODUCT.md 접근성 — 색 + 글자 + 점).

**② 목록 탭** — 격자를 몰라도 바로 손댈 수 있게, 같은 집계를 목록으로 둔다.
- 문서 없는 모델 자료
- 모델 없는 문서 자료(보고서에 사용한 모델 연결(21)도 없는 것)
- 해석 검증 실패만 있는 모델
- 보완 필요(20번 `needs_fix` — 필수 분류 빠짐)
- 서명 없는 모델(12 이전 변환)

**③ 칸을 누르면** 오른쪽 미리보기 패널에 그 칸의 자료 목록이 열린다(원칙 4 '떠나지 않고 보기'). 빈 칸이면 같은 호선의 다른 구역, 같은 구역의 다른 호선 자료를 "가까운 자료"로 보여 준다.

### 계산 — 관계 지도와 같은 방식
저장하지 않고 요청마다 묶는다(`backend/app/coverage.py`, `GET /api/coverage`).
- 자료: 확정 Entry + `visible_entries_filter(user)`
- 호선: `entry_hulls`, 공용: `entries.no_hull`, 프로젝트·구역: `entry_tags`(대표 값 `Vocab.root`)
- 모델/문서 유무: `files.kind`(`model`·`report`, 휴지통 제외)
- 모델↔문서 연결: `report_model_links`(21) — 문서만 있는 자료도 다른 자료의 모델과 이어져 있으면 '모델 없음'으로 세지 않는다
- 검증: `solve_checks.state`

응답 모양(초안):
```json
{
  "rows": [{"key": "hull:9999", "label": "9999", "ship_type": "LNGC", "kind": "hull"}],
  "cols": [{"key": "zone:정반", "label": "정반"}],
  "cells": [{"row": "hull:9999", "col": "zone:정반", "entries": 3, "models": 2, "reports": 1,
             "solve_fail_only": false, "atypes": ["Truss", "권상"]}],
  "lists": {"no_report": [...], "no_model": [...], "solve_fail": [...], "needs_fix": [...], "unsigned": [...]},
  "truncated": false
}
```
해석 종류 거르기는 프런트에서 `cells[].atypes`로 다시 센다. 그래서 요청은 한 번이면 된다.

### 크기 상한
호선 수백 × 구역 수십이면 격자가 화면을 넘는다.
- 행: 자료가 있는 호선만 나온다. 정렬은 최근 확정 순 또는 호선 번호 순 중 고른다.
- 열: 자료 수 상위 20개 구역만 펼치고, 나머지는 '기타'로 묶는다(누르면 펼침).
- `MAX_ENTRIES`는 관계 지도와 같은 3000으로 둔다.

### 나중 단계 — '있어야 할 목록'
지금의 빈칸은 상대적이다. 다른 호선에는 있는데 이 호선에는 없다는 뜻일 뿐이다.
관리자가 선종별 표준 해석 목록(예: LNGC = 정반 Truss · 권상 · 계류)을 정하면, **진짜 빠진 해석**을 빨간 칸으로 보일 수 있다.
표 `coverage_expectations(ship_type, zone, analysis_type)`가 필요하다. 1단계에는 넣지 않는다.

### 테스트
- 권한: LV1이 블록 자료 칸을 세지 않는다.
- 동의어: '정반'과 '정반 구역'이 같은 열로 모인다.
- 모델↔문서 연결: 링크로 이어진 문서 자료는 '모델 없음'에서 빠진다.
- 휴지통 파일은 세지 않는다.

## 27. 모델 특징 + 모델 점검

### 기반 — `model_features` 표
27의 점검과 28의 비슷한 선례가 같은 값을 쓴다. 변환(`convert/job.py run_convert`)이 이미 BDF를 한 번 다 읽으므로 그 자리에서 함께 계산한다. 다시 읽지 않는다.

```
model_features
  file_id        PK, FK files.id (CASCADE)
  version        특징 규칙 버전(bdf/features.py FEATURE_VERSION) — 다르면 비교하지 않는다
  vector         JSON  — 28의 유사도용 수치 벡터(고정 길이)
  stats          JSON  — 사람이 읽는 값(아래 표)
  checks         JSON  — 27 점검 결과 [{code, level, message, detail}]
  updated_at
```
재구축 대상이 아니다. 변환하면 다시 생기는 파생값이라 `solve_checks`와 같은 취급이다.
이미 변환된 모델은 `enqueue-convert --missing-features`로 채운다(12의 `--missing-signature`와 같은 방식).

**stats에 담는 값** (`bdf/features.py`, 순수 함수 + 테스트)

| 값 | 출처 | 쓰는 곳 |
|---|---|---|
| 요소 수(보·쉘·강체·질량), 절점 수 | `Model.counts()` | 27·28 |
| 크기 L ≥ W ≥ H(정렬한 bbox 치수) | `Model.bbox()` | 27(단위 추정)·28 |
| 평균 요소 크기 ≈ 크기 대각 / √요소 수 | 계산 | 27(촘촘함)·28 |
| 단면 목록(PBEAML 형상·치수), 쉘 두께 목록 | `Model.properties` + `fingerprint.section_label` | 28 |
| 재료 E·ν·ρ | `Model.materials` | 27 |
| 연결 그룹 수, 주 구조 비율 | `bdf/groups.connected_groups` | 27 |
| 자유 절점 수(요소에 안 쓰인 GRID) | 계산 | 27 |
| 같은 자리 절점 쌍 수(허용 0.01 × 평균 요소 크기) | 격자 해시 | 27 |
| 길이 0 요소 수 | 계산 | 27 |
| SPC 절점 수, 질량 합 | `Model.spcs`, `Model.masses` | 27 |
| **GRAV 방향·크기, FORCE 수** | 새로 읽음(아래 참고) | 27 |
| SOL | `Model.sol` | 28 |

GRAV·FORCE는 지금 `bdf/model.py`의 `IGNORED`에 있어 버려진다. `build_model`은 바꾸지 않는다. 대신 `features.py`가 카드 목록(`DeckReader.cards`)에서 GRAV·FORCE만 따로 센다. 뷰어 쪽 동작은 그대로 둔다.

### 점검 규칙 — 두 가지
**A. 모델 하나만 보고 판정하는 규칙** (`checks/rules.py`, 규칙마다 테스트)

| 코드 | 수준 | 판정 | 문장 예 |
|---|---|---|---|
| `unit_mismatch_E` | 주의 | 크기로 추정한 단위(mm: L > 500, m: L < 500)와 E 크기가 안 맞음(mm·MPa → E ≈ 2e5, m·Pa → E ≈ 2e11) | "모델 크기는 mm 단위인데 E = 2.06e11 — Pa 값으로 보입니다" |
| `density_missing` | 주의 | GRAV가 있는데 쓰인 재료의 ρ가 비었거나 0 | "자중(GRAV)을 거는데 MAT1 1번에 밀도가 없습니다 — 자중이 0이 됩니다" |
| `density_unit` | 주의 | mm 모델인데 ρ ≈ 7850(kg/m³) | "밀도 7850 — mm 단위 모델이면 7.85e-9가 맞습니다" |
| `no_spc` | 주의 | SOL 101인데 SPC 절점이 0 | "고정 조건이 없습니다 — 해석하면 mechanism으로 실패합니다" |
| `grav_direction` | 참고 | GRAV 방향이 z축과 다름(위로 향함 포함) | "중력이 +Z 방향입니다" |
| `split_groups` | 참고 | 연결 그룹 2개 이상 | "떨어진 덩어리 3개(주 구조 외 요소 41개)" |
| `coincident_nodes` | 참고 | 같은 자리 절점 쌍 > 0 | "같은 자리에 절점 12쌍 — 이어지지 않았을 수 있습니다" |
| `zero_length` | 주의 | 길이 0 보 요소 | "길이 0인 보 요소 2개" |
| `free_nodes` | 참고 | 요소에 안 쓰인 GRID | "어디에도 안 쓰인 절점 230개" |

수준은 **참고 / 주의** 두 가지다. '오류'를 두지 않는 이유는 확정을 막지 않기 때문이다. 해석 검증(06)의 실패가 이미 '오류' 역할을 한다.

**B. 비슷한 모델과 견주는 규칙** — 쌓일수록 정확해지는 쪽

같은 구역 + 해석 종류의 확정 모델이 5개 이상일 때만 판정한다. 그보다 적으면 말하지 않는다.
- 값: log(요소 수), 평균 요소 크기, 쉘 두께 중앙값, 단면 수
- 판정: 중앙값과 MAD로 구한 robust z가 3을 넘으면 '참고'
- 문장: "정반 · Truss 모델 14개보다 요소가 약 8배 많습니다(중앙값 3,200개, 이 모델 26,000개)"

B는 저장하지 않고 화면을 열 때 계산한다. 비교 대상이 늘면 결과가 바뀌기 때문이다. A는 `model_features.checks`에 저장한다.

### 화면
- **정리 대기 카드**(02b): BDF 칩 옆에 `점검 2` 배지를 단다. 누르면 문장 목록이 펼쳐진다. 확정 단추는 잠그지 않는다.
- **자료 상세 · 모델 미리보기**: '모델 점검' 접이식 칸. 해석 검증 배지(06) 바로 아래에 둔다.
- **3D 뷰어 연동**: `coincident_nodes`·`zero_length`·`free_nodes`·`split_groups`는 ID 목록을 함께 저장한다(최대 200개). 문장을 누르면 뷰어가 그 절점·요소를 강조한다. 16번 변경 보기의 강조 방식을 재사용한다.
- **빈칸 지도(26) 목록 탭**에 '점검 주의가 있는 모델'을 추가한다.

### WorkBench 오류 기록과 잇기 (나중 단계)
WorkBench `diagnostic_signatures`에는 운영 중 실제로 난 Nastran FATAL 유형이 쌓인다. 반복되는 FATAL 중 BDF만 보고 미리 알 수 있는 것(예: 2101 RBE2 종속 중복, 9994 하중 SID 충돌)을 규칙 A로 옮긴다.
LogBook은 이미 `wb_users.py`로 WorkBench DB를 읽기 전용으로 읽고 있으므로, 같은 방식으로 유형 목록을 읽어 '이 규칙이 막은 실제 사례 수'를 관리 화면에 보일 수 있다.

### 테스트
- `features.py`: 작은 BDF 문자열로 각 값을 고정한다(GRAV 방향, 같은 자리 절점, 길이 0).
- 규칙 A: 규칙마다 걸리는 BDF / 안 걸리는 BDF 한 쌍씩.
- 규칙 B: 비교 대상 4개 → 말하지 않음, 5개 → 판정. 권한 밖 자료는 비교 대상에서 빠진다.
- 운영 데이터 오탐 확인: 145의 확정 모델 전부에 규칙 A를 돌려 걸린 비율을 본다. WorkBench `bdf_deck_check` 도입 때처럼 오탐 0을 목표로 문턱을 맞춘다.

## 28. 비슷한 선례 찾기

### 무엇을 하나
BDF를 기준으로 과거 확정 자료 중 비슷한 모델을 순위로 보여 준다. 결과마다 **왜 비슷한지**와 그 자료의 **문서·판정**이 함께 나온다.

들어오는 길은 세 곳이다.
1. **자료 상세 → [비슷한 선례]**: 이미 있는 모델이 기준이다. 저장된 특징을 바로 쓴다.
2. **검색 화면에 BDF 끌어다 놓기**: 저장하지 않고 임시로 읽는다. 17번 동기 검사처럼 32MB/15초 상한을 두고, 넘으면 워커 임시 작업으로 넘긴다. 올린 파일은 지우고 공유 폴더에도 남기지 않는다.
3. **WorkBench Model Builder 결과 화면** (나중 단계): 18번 연동 API에 `POST /api/integration/similar`를 더한다. 공유 비밀키를 쓰고 `as=<사번>`으로 그 사람 권한 안에서만 찾는다.

### 점수 — 설명할 수 있게 항목별로
하나의 숫자만 내지 않는다. 항목별 점수를 남겨 화면에서 이유 문장을 만든다.

| 항목 | 계산 | 무게(초안) | 이유 문장 |
|---|---|---|---|
| 형상 | 서명 geometry 같음 → 1.0(바로 맨 위) | — | "형상이 같습니다(단면·하중만 다름)" — 관계 지도 '형상만 같음'과 같은 말 |
| 크기 | 정렬한 L·W·H의 log 거리 → exp(−d) | 0.30 | "크기 22 × 10 × 2 m로 비슷" |
| 규모·촘촘함 | log(요소 수), 평균 요소 크기 | 0.20 | "요소 3,100개 · 평균 450 mm" |
| 구성 | 보/쉘/강체/질량 비율의 코사인 | 0.20 | "보 위주(보 92%)" |
| 단면 | 단면 라벨 집합 Jaccard + 쉘 두께 겹침 | 0.20 | "단면 8개 중 6개 같음(L100x100x10 …)" |
| 분류 | 같은 구역 / 같은 해석 종류 | 0.10 | "같은 구역 · 같은 해석 종류" |

- 무게는 상수로 둔다(`similar/score.py`). 운영 데이터로 조정한 뒤 고정 테스트로 묶는다.
- 비교 대상이 수천 개 이하라 요청마다 메모리에서 전부 계산해도 충분하다. 벡터 색인은 쓰지 않는다.
- 같은 자료의 다른 판(14)은 한 줄로 묶어 최신 판만 보인다.

### 결과 한 줄
```
E000231  9999 · 정반 · Truss · 1차          유사 0.86
```

- [나란히 비교](07)로 기준 모델과 바로 연다. 형상이 같으면 [변경 보기](16)도 연다.
- 결과가 비슷하지 않으면(최고 점수 < 0.5) "충분히 비슷한 선례가 없습니다"라고 말한다. 억지로 채우지 않는다.

### API
- `GET /api/files/{id}/similar?limit=20` — 저장된 특징 기준
- `POST /api/similar` (multipart BDF) — 임시로 읽은 특징 기준. 응답 모양은 같다.
- 응답: `[{entry, file, score, parts: {shape, size, scale, mix, sections, tags}, reasons: [..], reports: [..], solve}]`

### 테스트
- 같은 형상 모델이 항상 맨 위에 온다.
- 크기만 10배 다른 모델은 크기 점수가 낮다.
- 권한 밖 자료는 결과에도, 개수에도 나오지 않는다.
- 판이 여러 개인 자료는 한 줄로 나온다.
- 임시 업로드 파일이 공유 폴더와 DB에 남지 않는다.

## 공통 — 발표 이야기와의 연결
- 빈칸 지도: "자료는 사람이 아니라 LogBook에 남는다" → **무엇이 남지 않았는지도 보인다**
- 모델 점검: "모델이 쌓일수록" → **쌓일수록 점검 기준(규칙 B)이 정확해진다**
- 비슷한 선례: 관계 지도는 보는 기능, 이건 **다음 해석에 바로 쓰는 기능**. WorkBench 사용자 약 180명이 해석 시작 전에 선례를 찾는 길이 된다.
